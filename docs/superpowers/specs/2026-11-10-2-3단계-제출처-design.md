## 1. 목표

보호자가 병원의 **제출처 태블릿**에서 가져온 모유 팩 수를 직접 입력한다. 간호사가 **실제 받은 수량을 확인**해야 재고에 반영된다. 원래 5단계였던 보호자 화면을 여기서 만든다.

완료 기준: 보호자 제출 → 간호사 확인 → 재고 반영이 여러 제출처에서 맞게 동작한다.

### 확정한 결정 (2026-11-11)
- **간호사의 직접 [입고]는 그대로 둔다.** 보호자가 태블릿을 거치지 않고 간호사에게 직접 건넬 때나 태블릿이 고장 났을 때 쓴다. 직접 입고 기록에는 지금처럼 입력 직원이 남는다.
- **보호자 화면에 확인 대기 팩 수를 따로 보여 준다.** "간호사 확인 기다리는 중 M팩"으로 표시해, 제출이 안 된 줄 알고 다시 입력하는 일을 줄인다.
- 제출처 한 대에서 로그인 실패가 몰리면 그 제출처를 잠근다(3.2).
- 한 아기의 확인 대기는 5건까지만 받는다(3.2).
- 제출처 모드를 해제하면 서버에서도 그 제출처를 비활성화한다(4.1).

### 범위
- **2-3a 서버**
  - **먼저** 마이그레이션 안전장치를 보강한다(2.1).
  - 그다음 마이그레이션 0002를 만든다.
  - 제출처·보호자·제출·확인 API
- **2-3b 앱**
  - 제출처 모드와 제출처 관리 화면
  - 보호자 화면
  - 간호사 홈의 입고 확인 대기 표와 수량 확인·반려
  - 에뮬레이터로 끝까지 확인
- 이번 단계 밖
  - 부족 안내 문구: 4단계 판정이 생긴 뒤에 만든다.
  - 반려 사실을 보호자에게 알리는 기능: 간호사가 직접 말한다.

## 2. 데이터

### 2.1 먼저: 마이그레이션 안전장치 (2-1 계획 완료 기록 참조)
- `migrations/env.py`의 `context.configure(...)`에 `transactional_ddl=True`를 넣는다.
- 끝까지 확인하는 테스트: 데이터 연결을 깨뜨리는 가짜 0002를 적용하면 오류가 나고, DB 버전과 데이터가 0001 상태 그대로 남아야 한다.
- README 개발자 안내의 `foreign_key_check` 설명이 실제 동작과 맞는지 확인한다.

### 2.2 마이그레이션 0002

| 표 | 칸 |
|---|---|
| `station` | id, name(1~20자, 사용 중인 제출처끼리 중복 불가 — 사용 중지한 이름은 다시 쓸 수 있음), token_hash(SHA-256, 중복 불가), active, created_at, created_by(staff) |
| `submission` | id, patient_id, station_id, count(1~10), submitted_at, status(`pending`/`confirmed`/`rejected`), confirmed_count(1~100, 확인했을 때만), handled_by(staff), handled_at, intake_record_id(만들어진 입고 기록), reject_reason(`not_received`/`other`), memo |
| `guardian_session` | id, token_hash(중복 불가), phone, station_id, created_at, last_seen_at |

- `submission`은 `status`가 `pending`일 때만 처리할 수 있다. 한 번 처리하면 다시 바꿀 수 없다.
  - 잘못 확인했으면 직원이 만들어진 입고 기록을 취소한다. 취소 규칙은 기존과 같다(간호사는 본인 기록 10분 이내, 관리자는 언제든).
  - 입고 기록을 취소해도 제출 상태는 `confirmed`로 남는다.
- 반려 사유가 `other`이면 메모(1~100자)가 꼭 있어야 한다.
- 로그인 실패 기록은 기존 `login_attempt` 표를 함께 쓴다.
  - 보호자: 키 `guardian:{정규화한 전화번호}`
  - 제출처: 키 `station:{id}`
- 퇴원 뒤 개인정보를 말소할 때 그 아기 제출의 `memo`도 지운다.
- 그 아기의 `guardian_session`은 퇴원할 때 끝낸다.

## 3. 서버 API

### 3.1 제출처 관리 (관리자)
- `POST /stations` `{name}` → `{station: {id, name, active, created_at}, station_token}`
  - 토큰은 이때 한 번만 돌려준다. 그 태블릿의 앱이 저장한다.
  - 이름이 겹치면 409 "이미 있는 제출처 이름입니다".
- `GET /stations` → 목록(이름순)
- `PATCH /stations/{id}` `{active: false}`
  - 그 기기의 보호자 세션을 모두 끝낸다.
  - 다시 켜는 기능은 두지 않는다. 다시 쓰려면 새로 등록한다(분실한 기기의 토큰이 되살아나지 않도록).
- `DELETE /station/self` (헤더 `X-Station-Token`)
  - 제출처 모드를 해제할 때 앱이 부른다.
  - 관리자 토큰도 함께 필요하다(관리자 로그인 뒤 해제).
  - 이 제출처를 비활성화한다.

### 3.2 보호자
요청마다 헤더 `X-Station-Token`이 필요하다.
- 토큰이 없거나, 모르는 토큰이거나, 비활성 제출처의 토큰이면 401 `station_invalid` "등록된 제출처 기기가 아닙니다".
- `GET /station/self` → `{id, name}`: 앱 첫 화면에 이름을 표시한다.
- `POST /guardian/login` `{phone, baby_id}` → `{token, babies: [...]}`
  - 전화번호는 기존 `normalize_phone`으로 맞춘다.
  - 그 전화번호의 입원 중인 아기 가운데 아기 ID가 일치하는 아기가 있으면 로그인된다.
  - `babies`에는 같은 전화번호의 입원 중인 아기를 모두 담는다(쌍둥이 등).
  - 실패하면 401 "전화번호 또는 아기 ID가 올바르지 않습니다". 어느 쪽이 틀렸는지 알려 주지 않는다.
  - 같은 전화번호로 5번 연속 실패하면 10분 동안 잠긴다(429). 없는 전화번호도 같은 규칙이 적용된다.
  - 같은 제출처에서 10분 안에 20번 실패하면 그 제출처의 보호자 로그인을 10분 동안 막는다(429 "잠시 뒤에 다시 시도해 주세요").
- `GET /guardian/babies` → `[{patient_id, baby_id, balance, pending_count}]`
  - 보호자 토큰이 필요하다. 자기 아기만 돌려준다.
  - `pending_count`는 확인 대기 제출의 팩 수 합계다.
- `POST /guardian/submissions` `{patient_id, count}` → `{submission: {id, count, submitted_at}, balance, pending_count}`
  - count는 1~10이고, 자기 아기만 제출할 수 있다(남의 아기면 403).
  - 퇴원한 아기는 409.
  - 그 아기의 확인 대기가 이미 5건이면 409 "확인을 기다리는 제출이 많습니다. 간호사에게 말씀해 주세요".
- `POST /guardian/logout`
- 보호자 토큰은 `Authorization: Bearer`로 보낸다(직원 토큰과 같은 방식, 다른 표). 직원 토큰으로 보호자 API를, 보호자 토큰으로 직원 API를 쓸 수 없다.
- 보호자 세션은 1분 동안 요청이 없으면 만료된다. 보호자 토큰은 그 세션을 만든 제출처 토큰과 함께 와야 유효하다.

### 3.3 간호사·관리자
- `GET /submissions?status=pending` → `[{id, patient_id, baby_id, balance, station_name, submitted_at, count, discharged}]` (접수 시각순)
- `POST /submissions/{id}/confirm` `{count}` → `{record, balance, submission}`
  - count는 1~100이다.
  - INTAKE 기록을 만든다. 메모는 "{제출처 이름} 제출분(제출 {n}팩)"이고, 입력 직원은 확인한 사람이다.
  - 이미 처리됐으면 409 "이미 처리된 제출입니다".
  - 퇴원한 아기는 409 "퇴원한 아기입니다. 반려만 할 수 있습니다".
- `POST /submissions/{id}/reject` `{reason, memo?}` → `{submission}`
  - 이미 처리됐으면 409.
- 모든 쓰기는 `BEGIN IMMEDIATE`로 직렬화한다. 두 간호사가 동시에 확인하면 한 명만 반영된다.

## 4. 앱

### 4.1 제출처 모드
- **켜기**
  - 관리자 홈 ⋮ 메뉴의 **"이 기기를 제출처로 사용"**에서 이름을 입력한다.
  - `POST /stations`로 등록하고, 받은 토큰을 DataStore에 Android Keystore(AES-GCM)로 암호화해 저장한다.
  - 관리자 세션을 끝낸다. 그 뒤로 앱은 시작할 때마다 **보호자 화면만** 보여 준다.
- **끄기**
  - 화면 왼쪽 위 구석을 3초 동안 길게 누르면 관리자 로그인 창이 뜬다. 기존 직원 로그인 API를 쓰고, 잠금 규칙도 같다. 관리자가 아니면 거절한다.
  - [제출처 모드 해제]를 누르면 `DELETE /station/self`를 부르고, 기기의 토큰을 지운 뒤 로그인 화면으로 간다.
  - 서버에 닿지 않으면 해제하지 않고 "서버에 연결된 뒤 다시 시도해 주세요"라고 안내한다.
- **제출처 관리 (관리자 메뉴)**
  - 제출처 목록(이름, 사용 중/중지)을 보여 준다.
  - [사용 중지]는 확인 창을 거친다.
- **제출처 토큰이 무효가 되면**(401 `station_invalid`)
  - "등록된 제출처 기기가 아닙니다. 직원에게 알려 주세요" 화면을 보여 준다.
  - 이 화면에서도 구석을 길게 눌러 관리자가 해제할 수 있다. 이때 서버 호출이 실패해도 기기의 토큰은 지운다.

### 4.2 보호자 화면 (예시 01·02)
1. **첫 화면**
   - "제출처 태블릿 · {제출처 이름}"을 보여 준다.
   - 보호자 전화번호(숫자 키패드)와 아기 ID를 입력하고 [확인]을 누른다.
2. **아기 선택**: 아기가 여러 명이면 아기 ID 목록에서 고른다.
3. **우리 아기 모유 재고**
   - "현재 확인된 냉동 모유 **N팩**"을 크게 보여 준다.
   - 확인 대기가 있으면 "간호사 확인 기다리는 중 M팩"을 작게 함께 보여 준다.
   - "재고만 보고 마칠 수도 있어요"
   - 버튼: [가져온 모유 입력] / [마치기]
4. **가져온 모유 입력**
   - 숫자 버튼 1~10 중 하나를 누른다.
   - 확인 창 "{아기 ID} 아기 모유 N팩을 제출합니다"에서 [제출]을 누른다.
5. **제출 접수 완료**
   - "방금 제출한 모유 N팩"
   - "현재 확인된 냉동 재고 M팩"
   - "제출한 N팩은 간호사 확인 후 재고에 반영됩니다"
   - [마치기]
6. **로그아웃**: [마치기]를 누르거나 1분 동안 조작이 없으면 로그아웃하고 첫 화면으로 돌아간다. 입력칸도 비운다.
   - 보호자 로그아웃은 2-2처럼 바로 처리하고, 서버에는 뒤에서 알린다.

공통 규칙
- 버튼은 높이 64dp 이상, 글씨는 크게 한다.
- 서버 연결이 끊기면 기존 띠를 보여 주고 버튼을 막는다.
- 저장 중 통신이 끊기면 다시 불러오고 "제출이 됐는지 확인하지 못했습니다. 재고 화면을 확인해 주세요"라고 안내한다. 확인 대기 팩 수로 확인할 수 있다.
- 보호자 화면에는 아기 ID만 보이고, 이름은 보이지 않는다.

### 4.3 간호사 홈 (예시의 첫 화면)
- 환자 목록 위에 **입고 확인 대기 N건** 표를 둔다. 대기가 없으면 숨긴다.
  - 칸: 아기 ID, 현재 냉동 재고, 제출 위치, 접수 시각(오후 2시 13분 형식, 오늘이 아니면 날짜도), 제출 팩 수, [수량 확인]
  - 30초마다(연결 확인과 함께), 앱으로 돌아올 때, 처리한 직후에 새로고침한다.
- **수량 확인 창**
  - 제목: "{아기 ID} · {제출처} · {접수 시각}"
  - 제출 팩 수가 미리 채워져 있고, −/+로 실제 받은 수를 고친다(1~100).
  - [확인]: 입고로 반영한다.
    - 결과 띠: "{아기 ID} · N팩 입고 확인 완료 · 현재 냉동 재고 M팩"
    - 예시 03처럼 "실제 받은 모유 N팩 / 현재 확인된 냉동 모유 M팩 / 기존 K팩 + 확인한 N팩"을 보여 준다.
  - [반려]: 사유(모유가 오지 않음 / 기타 + 메모)를 고른다. 재고는 바뀌지 않는다.
  - 409(이미 처리됨, 퇴원)이면 서버 문구를 보여 주고 표를 새로고침한다.
  - 통신이 끊기면 다시 불러오고 "처리됐는지 확인하지 못했습니다. 대기 표를 확인해 주세요"라고 안내한다.
- 퇴원한 아기의 대기 행에는 [수량 확인] 대신 [반려]만 둔다.

## 5. 예외

- **동시 확인**: 같은 제출을 두 간호사가 동시에 확인하면 한 명만 반영되고, 다른 한 명은 "이미 처리된 제출입니다"를 본다.
- **확인 대기 중 퇴원**: 확인할 수 없고 반려만 할 수 있다.
- **연속 제출**: 보호자가 같은 아기를 연속으로 제출하면 각각 대기 목록에 오른다. 5건까지 받는다. 간호사가 실제 수량으로 확인하거나 반려한다.
- **기기 분실**: 관리자가 그 제출처를 사용 중지하면 즉시 쓸 수 없게 된다.
- **장난 입력**: 같은 제출처에서 로그인 실패가 몰리면 그 제출처를 10분 동안 잠근다.

## 6. 테스트

- **서버 (2-3a)**
  - 안전장치: 깨진 가짜 0002가 롤백되고 버전이 0001에 남는다.
  - 0002 적용(데이터가 있는 DB 포함)과 표 정의 일치
  - 제출처 토큰이 없거나 비활성이면 401
  - 제출처 사용 중지 → 보호자 세션 종료
  - 보호자 로그인 성공(쌍둥이 목록 포함), 실패 문구, 전화번호 잠금, 제출처 잠금
  - 남의 아기 조회·제출은 403
  - 확인 대기 5건 제한
  - 제출 → 확인 → 잔량 증가, 수량을 고친 확인, 반려(잔량 그대로), 기타 사유의 메모 필수
  - 이중 확인 동시성
  - 퇴원한 아기의 확인 막기와 반려 허용
  - 보호자 세션 1분 만료
  - 말소할 때 제출 메모 삭제
- **앱 (2-3b)**
  - 제출처 모드 켜기·해제, 토큰 무효 화면
  - 보호자 흐름: 조회 → 입력 → 접수 완료 → 마치기·1분 자동 로그아웃
  - 간호사 대기 표 → 수량 확인 → 결과 띠, 반려, 409 처리, 통신이 끊긴 처리
  - 에뮬레이터로 실제 서버와 끝까지 확인
    - 원칙은 두 대(제출처 + 간호사)다.
    - 이 PC에서 두 대를 동시에 켜기 어려우면 한쪽은 API 호출 스크립트로 대신하고, 그 사실을 기록한다.
